# C-08 분류 검수 백엔드

기준: 작업파일 `261023/c08-review/12_C-08_표_줄이기_제안.md`, `13_C-08_기간기준_단일표_DB제안.sql`. 초기 `01`·`07` SQL은 실행하지 않는다.

## API

- `GET /api/c08/samples?runId=<77번 숫자>&gu=`: 운영자는 관련 여부·유형 검수 표본을 본다. 구 도로관리팀은 ISS-016 유형 목록과 표본 수가 정해질 때까지 빈 목록을 받는다. 시 도로과는 403.
- `POST /api/c08/samples/{sampleId}/review`: `{ "result": "맞음" }` 또는 `{ "result": "고침", "relevance": "관련|비관련|불명", "label": "..." }`. `sampleId`는 표본 스냅샷의 ID. 표본당 한 번만 저장한다. 구는 관련 여부를 보낼 수 없다.
- `GET /api/c08/accuracy?runId=<77번 숫자>`: 운영자만. `relevance`(관련 여부 정확도)와 `type`(유형 정확도)를 계속 분리한다. 각각 검수 전후 해당 항목이 같은 건수를 확인 완료 건수로 나눈다. 운영자가 유형만 고치면 관련 여부 정답으로 센다. 유형 지표는 ISS-016 전에는 `no_data`.
- `GET /api/c08/evaluation?runId=<77번 숫자>&target=relevance|pedType`: 운영자만. 관련 여부 평가 자료는 운영자 표본에서, 유형 평가 자료는 구 유형 검수 표본에서 만든다. 입력은 가린 요약만 쓰며 내려받기는 70 접근 기록에 남긴다. 신고 분류 낱말 규칙을 자동으로 고치지 않는다.

응답은 공통 미들웨어가 `camelCase`로 바꾼다. `masked_summary`만 `summary`로 내보내고 원문·위치·좌표는 내보내지 않는다. `class_reason` 문장은 현재 프론트 목업의 `keywords` 칸으로 보낸다.
이전 API의 `uploadId` 쿼리를 보내면 조용히 무시하지 않고 422 `upload_filter_removed`를 돌려준다.

## DB 선행 조건

DB v2.1에 작업파일 `13_C-08_기간기준_단일표_DB제안.sql`의 구조가 반영되어야 한다. 77 회차의 `period_start`·`period_end`는 **회차 생성 시** 정한다. C-08은 첫 조회 때 79에서 이 접수 기간 안의 현재 민원을 후보로 삼는다. 선택 업로드·업로드별 정확도는 사용하지 않는다. 사람 수정값과 판단 방법이 없는 행, 가린 요약이 없는 행은 시스템 분류 정확도 모집단에서 제외한다.

첫 GET 때 전체 구의 운영자 표본·선정 당시 가린 요약·분류값·층별 모집단을 `complaint_review`에 한 거래로 고정하고 77 `admin_sampled_at`에 완료 시각을 남긴다. 0건이어도 완료 시각을 남겨 뒤에 들어온 민원이 같은 회차 표본에 붙지 않게 한다. 구 유형 표본은 ISS-016 확정 뒤 별도 `district_sampled_at`으로 관리한다. 검수 저장 때 현재 79의 구·접수일·표시 내용·분류값이 선정 당시와 달라졌으면 409 `sample_changed`를 돌려준다. 분류를 고칠 때는 검수 표, 79 수정, 80 변경 이력, 70 접근 기록을 한 거래로 묶는다.

## 공통 파일 연결

인계 문서의 작업 범위를 지키기 위해 `app/main.py`는 수정하지 않았다. 통합 시 `ROUTER_MODULES`에 다음 한 줄을 추가해야 실제 서버에 API가 등록된다.

```python
("C-08", "app.api.c08_review_api"),  # /api/c08 분류 검수
```

프론트 목업의 `r2027` 같은 회차 ID는 실제 백엔드의 숫자 `77 priority_run.run_id`로 연결한다. 목업의 `markClassify*` 호출은 실제 API 주소·본문으로 바꿔야 한다. 어드민 유형 선택지는 ISS-016 전에는 빈 목록이므로, 프론트에서 유형 변경 입력을 숨기고 관련 여부 변경만 제공해야 한다.
